Laboratorio de métodos de Join SQL Tuning · Nested Loops vs Hash Join vs Sort Merge Join

Contexto

Laboratorio basado en el capítulo 9.2 «Joins Methods» del Oracle Database SQL Tuning Guide. Se plantean tres escenarios y en cada uno se fuerza cada método de join con hints para comparar los planes de ejecución.

Objetivo

Entender en qué situación el optimizador de Oracle favorece cada método de join y por qué.

Aspectos relevantes de la solución

  • Escenario A: 200 pedidos filtrados a 10 contra 50.000 productos con índice por clave primaria. Gana NESTED LOOPS, porque busca cada producto por índice.
  • Escenario B: dos tablas grandes, sin índices y con unión por igualdad. Gana HASH JOIN: Nested Loops tendría que escanear la tabla grande una y otra vez, y Sort Merge pagaría el costo de ordenar.
  • Escenario C: unión por rango (BETWEEN) entre 50.000 clientes y 5 rangos de edad. Un hash join solo sirve para igualdad, así que el hint no se puede aplicar y compiten Nested Loops y Sort Merge.
  • Se usó EXPLAIN PLAN con DBMS_XPLAN.DISPLAY y NO_PARALLEL para que el paralelismo no distorsione la comparación.

Resultados

Cada escenario se resolvió comparando el costo y las operaciones de los tres planes. El método ganador coincide con el que predice la teoría para cada caso.

Lo aprendido

No existe un método de join «mejor» en general: depende del tamaño de las tablas, de si hay índice sobre la columna de unión y del tipo de condición (igualdad o rango). Los hints sirven para comparar, pero normalmente conviene dejar que el optimizador decida con buenas estadísticas.

Fragmento clave

-- Mismo join, tres métodos forzados con hints
SELECT /*+ USE_NL(pe pr) */    ...   -- Nested Loops
SELECT /*+ USE_HASH(pe pr) */  ...   -- Hash Join
SELECT /*+ USE_MERGE(pe pr) */ ...   -- Sort Merge Join
FROM   pedidos pe
JOIN   productos pr ON pe.id_producto = pr.id_producto
WHERE  pe.id_pedido <= 10;

Optimización de consultas avanzadas e índices en Oracle 22 casos poco comunes de tuning · nivel avanzado

Contexto

Laboratorio de nivel avanzado, escrito en SQL puro, que recorre 22 casos raros de optimización en Oracle donde el plan de ejecución no se comporta como se esperaría.

Objetivo

Reconocer situaciones en las que un índice no se usa, el optimizador estima mal o una consulta devuelve resultados inesperados, y saber cómo diagnosticarlas y corregirlas.

Aspectos relevantes de la solución

  • Índices y tipos de datos: NULLs en índices B-tree, conversión implícita de tipos, Index Skip Scan, índices globales vs locales en tablas particionadas y bitmap join.
  • Estadísticas y estabilidad de planes: estadísticas extendidas, bind peeking, cardinality feedback, SQL Plan Baselines y SQL Plan Directives.
  • Transformaciones del optimizador: OR Expansion, Table Expansion, Join Factorization, Bloom Filters y planes adaptativos.
  • Herramientas: SQL Tuning Advisor (DBMS_SQLTUNE), indexación automática y Hint Usage Reports.
  • El caso 22 integra varios temas en un bug «intermitente» típico de producción.

Resultados

Cada caso incluye su preparación, la consulta problemática, el plan observado, la corrección y preguntas de análisis. Algunas secciones requieren Oracle 12c/19c o superior y privilegios de DBA.

Lo aprendido

Un ejemplo claro es NOT IN contra NOT EXISTS: si la subconsulta devuelve aunque sea un NULL, NOT IN no devuelve ninguna fila, mientras que NOT EXISTS sigue funcionando. Más en general, muchos problemas de rendimiento vienen de estadísticas desactualizadas, tipos de datos mal comparados o NULLs, y no de la falta de un índice.

Fragmento clave (caso 18)

-- NOT IN: devuelve 0 filas si la subconsulta trae algún NULL
... WHERE id_depto NOT IN (SELECT id_depto FROM lab_notin_emp);

-- NOT EXISTS: ignora los NULL de la subconsulta
... WHERE NOT EXISTS (SELECT 1 FROM lab_notin_emp e
                      WHERE  e.id_depto = d.id_depto);

Taller PL/SQL — Grupo 2 Sistema de inventario y pedidos · trabajo en equipo de tres integrantes

Contexto

Taller del curso (50 puntos) sobre un esquema de inventario con productos, categorías, clientes, pedidos y movimientos de stock. Cada objeto debía llevar su justificación de diseño y un análisis de cómo se comporta ante concurrencia, volumen y errores. Lo desarrollamos entre Erik Bautista, Felipe López y Mariana Durán.

Objetivo

Aplicar los principales elementos de PL/SQL a un caso realista y argumentar cada decisión técnica.

Aspectos relevantes de la solución

  • Procedimientos: SP_REGISTRAR_PRODUCTO, SP_AJUSTAR_STOCK y SP_CREAR_PEDIDO, con validaciones antes de consumir secuencias.
  • Funciones: FN_STOCK_DISPONIBLE, FN_CUPO_DISPONIBLE y FN_CALCULAR_DESCUENTO.
  • Cursores: cursores explícitos, ciclos FOR y operaciones masivas con FORALL.
  • Excepciones: excepciones propias, SP_VALIDAR_DESPACHO, SP_ANULAR_PEDIDO y SP_REGISTRAR_ERROR como transacción autónoma, para que el log del error sobreviva al ROLLBACK.
  • Disparadores: como TRG_CLIENTE_BI, que normaliza el nombre y asigna el id y el estado antes de insertar.
  • Caso integrador: el paquete PKG_VENTAS con SP_FACTURAR_PEDIDO, que reúne cursor, descuento, validación de cupo y SAVEPOINT.

Resultados

Se entregó el script completo junto con un documento con las salidas de DBMS_OUTPUT de cada prueba, además de una sustentación de 20 minutos por grupo.

Lo aprendido

Un ejemplo es el código duplicado: no basta con un SELECT previo, porque otra sesión puede insertar el mismo valor entre el SELECT y el INSERT. La restricción única es la que lo garantiza y el procedimiento solo traduce el error. También aprendimos a justificar por qué se elige una construcción y no otra, no solo a describir qué hace el código.

Fragmento clave

INSERT INTO PRODUCTO (...)
VALUES (SEQ_PRODUCTO.NEXTVAL, ...)
RETURNING id_producto INTO PARAM_idProducto;
EXCEPTION
  WHEN DUP_VAL_ON_INDEX THEN
    IF INSTR(UPPER(SQLERRM), 'UK_PRODUCTO_CODIGO') > 0 THEN
      RAISE e_codigo_duplicado;
    ELSE
      RAISE;  -- otra restriccion (por ejemplo la PK): no mentir
    END IF;

Taller MQL: consultas, agregación, índices y modelado MongoDB · sample_mflix · 15 puntos y 2 modelos en Hackolade · trabajo en pareja

Contexto

Taller de Bases de Datos 2 que hicimos Erik Bautista y Felipe López. Las partes A a C se resuelven sobre sample_mflix, el dataset de películas de MongoDB Atlas. La parte D pide modelar dos casos con patrones de diseño documental.

Objetivo

Practicar consultas, agregaciones, escritura e índices en MQL, y justificar las decisiones de modelado.

Aspectos relevantes de la solución

  • Parte A: filtros sobre arreglos (cast, genres, directors) con $all, $size, $ne, $or, $exists y expresiones regulares. Por ejemplo, 176 dramas entre 2000 y 2010 con rating de 8 o más, y 971 películas con exactamente tres géneros que incluyen Comedy y Romance.
  • Parte B: promedio y máximo por género, top de directores, películas por década, un $lookup entre comments y movies, y los usuarios con más de 250 comentarios. Como imdb.rating trae valores vacíos, filtramos por tipo numérico.
  • Parte C: la colección peliculas_pareja se creó con $out y $switch (Alta, Media o Baja). Después hicimos un updateMany sobre 231 películas Media, un deleteMany de las 62 Baja y un explain("executionStats") antes y después de crear un índice compuesto con la regla ESR.
  • Parte D: dos modelos. Uno es una plataforma de domicilios (Extended Reference, Subset, Computed y Attribute) y el otro un monitoreo de calidad del aire en Bogotá (Bucket, Computed y Schema Versioning). Cada uno lleva JSON de ejemplo, índices y dos consultas MQL.

Resultados

El zip trae el script .mongodb.js, el PDF con las capturas y la explicación de cada punto, y los dos modelos exportados de Hackolade. Sin índice, la consulta del punto 1 hace COLLSCAN. Con el índice compuesto pasa a IXSCAN y examina menos documentos.

Lo aprendido

En una agregación, el texto vacío se ordena después de cualquier número, así que un rating "" habría caído en la categoría Alta. Filtrar con $type: "number" evita ese error. En el caso del aire, el patrón Bucket reduce 288.000 documentos diarios (200 sensores, una lectura por minuto) a 4.800, es decir 60 veces menos.

Fragmento clave (punto 14)

// Indice ESR: igualdad (genres), orden (imdb.rating), rango (year)
db.movies.createIndex(
  { genres: 1, "imdb.rating": -1, year: 1 },
  { name: "idx_genres_rating_year" }
);

Práctica MQL individual: 30 ejercicios sobre Airbnb MongoDB · sample_airbnb · colección listingsAndReviews

Contexto

Práctica individual de MQL sobre la colección listingsAndReviews de sample_airbnb. Tiene 30 ejercicios agrupados por tipo de operación.

Objetivo

Manejar las operaciones CRUD y el pipeline de agregación sobre documentos con objetos anidados y arreglos.

Aspectos relevantes de la solución

  • Ejercicios 1 a 5, inserciones: insertOne con objeto anidado, insertMany con arreglos y una inserción con _id repetido que debe fallar con E11000.
  • Ejercicios 6 a 15, consultas: $gt, $lt, $and, $in, regex sin distinguir mayúsculas, búsqueda en arreglos con $size, proyección, orden y límite.
  • Ejercicios 16 a 20, actualizaciones: $set, $push, $inc, $pull y un upsert con $setOnInsert.
  • Ejercicios 21 a 30, agregaciones: $group, $unwind, $project con $toInt, $bucket por rangos de precio, $lookup y conteo por año con $year.

Resultados

Un solo script con los 30 ejercicios comentados. El 28 es teórico, porque su $lookup apunta a una colección hosts que no existe en el dataset.

Lo aprendido

El precio se guarda como decimal, así que para usarlo en $bucket hubo que convertirlo antes con $toDouble. También vi que { last_review: null } encuentra tanto los documentos sin el campo como los que lo tienen en nulo.

Fragmento clave (ejercicio 27)

db.listingsAndReviews.aggregate([
  { $match: { price: { $exists: true } } },
  { $addFields: { precio_num: { $toDouble: "$price" } } },
  { $bucket: { groupBy: "$precio_num",
      boundaries: [0, 101, 301, 1001], default: "1000+",
      output: { cantidad: { $sum: 1 } } } }
]);

Proyecto final: base relacional en MySQL SistemaHorario · scripts SQL · lógica de negocio en la base de datos

Contexto

Scripts MySQL 8.4 de SistemaHorario, el sistema de gestión de horarios académicos del proyecto final, que hicimos Felipe López y Erik Bautista. Las reglas de negocio viven en la base de datos.

Objetivo

Implementar el esquema y las reglas de inscripción de modo que se cumplan aunque alguien escriba directo en las tablas.

Aspectos relevantes de la solución

  • Esquema de 19 tablas normalizado hasta 3FN, con relaciones 1:1, 1:N y N:M. aula es una entidad débil con llave compuesta.
  • Los procedimientos sp_inscribir_estudiante y sp_retirar_estudiante llevan su propia transacción, hacen ROLLBACK ante cualquier error y lanzan errores propios del 30001 al 30005. La inscripción bloquea la fila del grupo con FOR UPDATE, para que dos estudiantes no tomen el último cupo a la vez.
  • Dos funciones (fn_cupos_disponibles y fn_creditos_inscritos), tres triggers para validar el cupo y auditar inscripciones y retiros, y tres restricciones CHECK.
  • Dos usuarios con privilegios mínimos: horarios_app y horarios_lector.

Resultados

Seis scripts: esquema, lógica de negocio, datos de prueba, pruebas, secciones de demostración y reportes. Las 33 pruebas automáticas imprimen OK o FALLA. Los reportes son 18 consultas y 2 vistas que cubren cupos por grupo, carga docente, ocupación de aulas, horario del estudiante y control de choques.

Lo aprendido

Un procedimiento con su propio COMMIT no se mezcla con una transacción de Spring, por eso el servicio de inscripción corre sin @Transactional. Repetir la validación de cupo en un trigger deja una segunda barrera si alguien inserta directo. Al documentar el código también aparecieron límites: la tabla seccion no impide por sí sola los choques de aula o docente, y la inscripción no valida prerrequisitos.

Fragmento clave

START TRANSACTION;
-- Bloquea la fila del grupo: dos inscripciones simultaneas
-- no pueden pasarse del cupo
SELECT g.estado_grupo, g.cupo_maximo, g.id_curso, c.nombre_curso
  INTO v_estado_grupo, v_cupo_max, v_id_curso, v_nombre_curso
  FROM grupo g JOIN curso c ON c.id_curso = g.id_curso
 WHERE g.id_grupo = p_id_grupo
   FOR UPDATE;

Proyecto final: base documental en MongoDB SistemaHorario · horarios_nosql · historial, bitácora y notificaciones

Contexto

Base horarios_nosql en MongoDB 8.0, que complementa a MySQL en SistemaHorario. Guarda lo que el modelo relacional descarta: cada generación reemplaza el horario vigente y las inscripciones rechazadas no dejan rastro.

Objetivo

Conservar historial y trazabilidad en documentos de forma variable sin tocar la integridad transaccional de MySQL.

Aspectos relevantes de la solución

  • Tres colecciones con validación $jsonSchema e índices: historial_generaciones (una foto de cada generación, con sus secciones embebidas), bitacora_eventos (inscripciones y retiros, incluidos los rechazados) y notificaciones (correos de verificación).
  • CRUD con inserción, actualización de elementos dentro de arreglos y depuración de notificaciones viejas.
  • Cinco consultas complejas, entre ellas los rechazos por falta de cupo y las generaciones con una materia en cierto día, que consulta el arreglo embebido.
  • Siete agregaciones: eventos por tipo, demanda real por grupo, motivos de rechazo, secciones por día con $unwind, carga docente, tasa de éxito y serie diaria con $dateToString.

Resultados

Cuatro scripts de mongosh: crear colecciones, datos de ejemplo, CRUD con consultas y agregaciones. Las mismas agregaciones alimentan el endpoint /api/horarios/nosql/resumen del back.

Lo aprendido

Guardar una foto de cada generación resolvió la auditoría sin cambiar el modelo relacional, y si MongoDB cae las inscripciones siguen funcionando. Falta el patrón outbox, que evitaría que la bitácora pierda eventos si el servicio se cae.

Fragmento clave (A2)

// Demanda real: inscripciones exitosas por grupo
db.bitacora_eventos.aggregate([
  { $match: { tipo: "INSCRIPCION", resultado: "OK" } },
  { $group: { _id: "$grupo", inscripciones: { $sum: 1 } } },
  { $sort: { inscripciones: -1 } }

Proyecto final: documentación y gestión SistemaHorario · 12 documentos Word y 4 diagramas

Contexto

Documentación del proyecto final de Felipe López Almanza y Erik Bautista (noviembre de 2026). El sistema tiene un front en Jakarta Faces, una API REST en Spring Boot con Java 21, MySQL 8.4 y MongoDB 8.0. Las dos bases corren en máquinas virtuales con Ubuntu Server 24.04 LTS.

Objetivo

Dejar por escrito el problema, las decisiones técnicas, la implementación y la gestión del proyecto.

Aspectos relevantes de la solución

  • Propuesta, supuestos e informe ejecutivo, con cada decisión técnica y sus alternativas. Ubuntu frente a RHEL, por ejemplo, salió con un costo a cinco años de USD 17.572 frente a USD 19.592.
  • Análisis de MySQL frente a MongoDB, diccionario de datos y documentos de implementación de las bases, de las máquinas virtuales y del modelo en MongoDB.
  • Diagramas entidad-relación, relacional, de tablas reducidas y de arquitectura.
  • Gestión con 14 requerimientos funcionales y 9 no funcionales, 8 riesgos, matriz RACI, EDT y un cronograma de 16 semanas con 6 hitos.
  • Algoritmo genético para generar el horario: población de 80, hasta 500 generaciones, cruce de 0,85 y mutación de 0,12.

Resultados

12 documentos Word y 4 diagramas, más el enlace al repositorio del código del sistema.

Lo aprendido

Los documentos de un proyecto anterior, que usamos como punto de partida, traían versiones, fechas y licencias erróneas. Las corregimos contrastando con fuentes oficiales. Documentar el código también mostró pendientes, como guardar las claves de usuario con hash en vez de texto plano.
