Laboratorio de métodos de Join SQL Tuning · Nested Loops vs Hash Join vs Sort Merge Join

Contexto

Laboratorio basado en el capítulo 9.2 «Joins Methods» del Oracle Database SQL Tuning Guide. Se plantean tres escenarios y en cada uno se fuerza cada método de join con hints para comparar los planes de ejecución.

Objetivo

Entender en qué situación el optimizador de Oracle favorece cada método de join y por qué.

Aspectos relevantes de la solución

  • Escenario A: 200 pedidos filtrados a 10 contra 50.000 productos con índice por clave primaria. Gana NESTED LOOPS, porque busca cada producto por índice.
  • Escenario B: dos tablas grandes, sin índices y con unión por igualdad. Gana HASH JOIN: Nested Loops tendría que escanear la tabla grande una y otra vez, y Sort Merge pagaría el costo de ordenar.
  • Escenario C: unión por rango (BETWEEN) entre 50.000 clientes y 5 rangos de edad. Un hash join solo sirve para igualdad, así que el hint no se puede aplicar y compiten Nested Loops y Sort Merge.
  • Se usó EXPLAIN PLAN con DBMS_XPLAN.DISPLAY y NO_PARALLEL para que el paralelismo no distorsione la comparación.

Resultados

Cada escenario se resolvió comparando el costo y las operaciones de los tres planes. El método ganador coincide con el que predice la teoría para cada caso.

Lo aprendido

No existe un método de join «mejor» en general: depende del tamaño de las tablas, de si hay índice sobre la columna de unión y del tipo de condición (igualdad o rango). Los hints sirven para comparar, pero normalmente conviene dejar que el optimizador decida con buenas estadísticas.

Fragmento clave

-- Mismo join, tres métodos forzados con hints
SELECT /*+ USE_NL(pe pr) */    ...   -- Nested Loops
SELECT /*+ USE_HASH(pe pr) */  ...   -- Hash Join
SELECT /*+ USE_MERGE(pe pr) */ ...   -- Sort Merge Join
FROM   pedidos pe
JOIN   productos pr ON pe.id_producto = pr.id_producto
WHERE  pe.id_pedido <= 10;

Optimización de consultas avanzadas e índices en Oracle 22 casos poco comunes de tuning · nivel avanzado

Contexto

Laboratorio de nivel avanzado, escrito en SQL puro, que recorre 22 casos raros de optimización en Oracle donde el plan de ejecución no se comporta como se esperaría.

Objetivo

Reconocer situaciones en las que un índice no se usa, el optimizador estima mal o una consulta devuelve resultados inesperados, y saber cómo diagnosticarlas y corregirlas.

Aspectos relevantes de la solución

  • Índices y tipos de datos: NULLs en índices B-tree, conversión implícita de tipos, Index Skip Scan, índices globales vs locales en tablas particionadas y bitmap join.
  • Estadísticas y estabilidad de planes: estadísticas extendidas, bind peeking, cardinality feedback, SQL Plan Baselines y SQL Plan Directives.
  • Transformaciones del optimizador: OR Expansion, Table Expansion, Join Factorization, Bloom Filters y planes adaptativos.
  • Herramientas: SQL Tuning Advisor (DBMS_SQLTUNE), indexación automática y Hint Usage Reports.
  • El caso 22 integra varios temas en un bug «intermitente» típico de producción.

Resultados

Cada caso incluye su preparación, la consulta problemática, el plan observado, la corrección y preguntas de análisis. Algunas secciones requieren Oracle 12c/19c o superior y privilegios de DBA.

Lo aprendido

Un ejemplo claro es NOT IN contra NOT EXISTS: si la subconsulta devuelve aunque sea un NULL, NOT IN no devuelve ninguna fila, mientras que NOT EXISTS sigue funcionando. Más en general, muchos problemas de rendimiento vienen de estadísticas desactualizadas, tipos de datos mal comparados o NULLs, y no de la falta de un índice.

Fragmento clave (caso 18)

-- NOT IN: devuelve 0 filas si la subconsulta trae algún NULL
... WHERE id_depto NOT IN (SELECT id_depto FROM lab_notin_emp);

-- NOT EXISTS: ignora los NULL de la subconsulta
... WHERE NOT EXISTS (SELECT 1 FROM lab_notin_emp e
                      WHERE  e.id_depto = d.id_depto);

Taller PL/SQL — Grupo 2 Sistema de inventario y pedidos · trabajo en equipo de tres integrantes

Contexto

Taller del curso (50 puntos) sobre un esquema de inventario con productos, categorías, clientes, pedidos y movimientos de stock. Cada objeto debía llevar su justificación de diseño y un análisis de cómo se comporta ante concurrencia, volumen y errores. Lo desarrollamos entre Erik Bautista, Felipe López y Mariana Durán.

Objetivo

Aplicar los principales elementos de PL/SQL a un caso realista y argumentar cada decisión técnica.

Aspectos relevantes de la solución

  • Procedimientos: SP_REGISTRAR_PRODUCTO, SP_AJUSTAR_STOCK y SP_CREAR_PEDIDO, con validaciones antes de consumir secuencias.
  • Funciones: FN_STOCK_DISPONIBLE, FN_CUPO_DISPONIBLE y FN_CALCULAR_DESCUENTO.
  • Cursores: cursores explícitos, ciclos FOR y operaciones masivas con FORALL.
  • Excepciones: excepciones propias, SP_VALIDAR_DESPACHO, SP_ANULAR_PEDIDO y SP_REGISTRAR_ERROR como transacción autónoma, para que el log del error sobreviva al ROLLBACK.
  • Disparadores: como TRG_CLIENTE_BI, que normaliza el nombre y asigna el id y el estado antes de insertar.
  • Caso integrador: el paquete PKG_VENTAS con SP_FACTURAR_PEDIDO, que reúne cursor, descuento, validación de cupo y SAVEPOINT.

Resultados

Se entregó el script completo junto con un documento con las salidas de DBMS_OUTPUT de cada prueba, además de una sustentación de 20 minutos por grupo.

Lo aprendido

Un ejemplo es el código duplicado: no basta con un SELECT previo, porque otra sesión puede insertar el mismo valor entre el SELECT y el INSERT. La restricción única es la que lo garantiza y el procedimiento solo traduce el error. También aprendimos a justificar por qué se elige una construcción y no otra, no solo a describir qué hace el código.

Fragmento clave

INSERT INTO PRODUCTO (...)
VALUES (SEQ_PRODUCTO.NEXTVAL, ...)
RETURNING id_producto INTO PARAM_idProducto;
EXCEPTION
  WHEN DUP_VAL_ON_INDEX THEN
    IF INSTR(UPPER(SQLERRM), 'UK_PRODUCTO_CODIGO') > 0 THEN
      RAISE e_codigo_duplicado;
    ELSE
      RAISE;  -- otra restriccion (por ejemplo la PK): no mentir
    END IF;
